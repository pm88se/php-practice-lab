# SQL-002 — Concurrent Inventory Reservation

**EAV: 20–30 minutes** · Base · MySQL 8.4 / InnoDB · PDO

## Business scenario

Two shoppers try to purchase the **last available unit** of the same SKU.
Only one reservation can succeed; the other must not cause negative stock
or report a successful reservation.

## Your task

Implement only `reserve(PDO $pdo, int $productId): bool` in
`mysql/src/Sql002InventoryReservation.php`.

- The table `inventory` contains `product_id`, `sku`, `available`.
- Product 100 starts with 1 available unit; product 200 has 3.
- Use `beginTransaction()`, **`SELECT ... FOR UPDATE`**, and an UPDATE
  using the *same* PDO connection.
- Return `true` after committing exactly one unit decrement.
- Return `false` if the product does not exist or is sold out.
- On any SQL exception, roll back the transaction, then rethrow.
- Don't use an external framework, ORM, sleeps or artificial retry loops.
- Keep the implementation compact.

**Important:** `SELECT ... FOR UPDATE` only holds a locking read over the
transaction's lifetime. Do not commit between the SELECT and UPDATE.

## Concurrency test

The harness opens **two independent PDO connections**.
Session A starts a transaction and locks product 100 using
`SELECT ... FOR UPDATE` without committing.
Session B attempts the reservation and reaches its deliberately short
InnoDB lock wait timeout (1 second). Its transaction must be rolled back.
Session A then rolls back, and Session B retries successfully.

The timeout is intentionally used to observe a blocked row. In a real
application it is not the normal success path for purchasing.

## Run

```bash
php mysql/tests/run.php
```

## Scope

This exercise is about row-level locks and transaction boundaries,
not deadlock retries, payment workflows, or a full reservation lifecycle.
