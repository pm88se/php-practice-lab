# SQL-003 — Understanding InnoDB Shared Locks

**EAV: 20–30 minutes** · MySQL 8.4 / PDO

## What is a shared lock?

When a transaction executes `SELECT ... FOR SHARE` (older syntax:
`LOCK IN SHARE MODE`), InnoDB acquires a **shared (S) row lock**.

- **S + S:** two transactions may hold shared locks on the same row at once.
- **S + X:** a concurrent exclusive lock (e.g. an UPDATE) must wait.
- **X + S:** a shared locking read waits for an existing exclusive lock.
- A normal consistent `SELECT` generally uses MVCC and does not wait for
  an S lock.

A shared lock is not a general-purpose faster `SELECT`. It is a way to
protect a row from modification while a transaction depends on it.
The lock persists until the transaction commits or rolls back.
If two shared-lock holders later try to UPDATE the same row, lock upgrades
can deadlock: do not confuse S locks with write permission.

## Scenario

Two independent readers check the last unit of a product and need the
row to remain unchanged until they finish their checks. A stock-changing
writer should wait until **both readers** release their shared locks.

## What tests demonstrate

- A plain consistent SELECT remains readable via a third session.
