# SQL-003 — InnoDB Shared Locks (FOR SHARE)

**EAV: 15–25 minutes** · Base · MySQL 8.4 / InnoDB · PDO

## Goal

Learn how InnoDB **shared row locks** behave in real SQL sessions.
Unlike SQL-002's exclusive locking read (`FOR UPDATE`), two transactions
can hold a shared lock on the same row at the same time.

This is a small MySQL-feature lab, not a full application scenario.

## Implement

`Sql003SharedLock::readAvailable(PDO $pdo, int $productId): ?int`
in `mysql/src/Sql003SharedLock.php`.

- Read `inventory.available` for one product by primary key.
- Acquire an InnoDB shared lock using `FOR SHARE` (preferred MySQL 8.4 syntax)
  or the legacy `LOCK IN SHARE MODE`.
- Return the integer stock count; return `null` when no product exists.
- The **caller already opened the transaction**. Do **not** call
  `beginTransaction()`, `commit()`, or `rollBack()` inside this method.
  The locking read must hold its lock *after your method returns*.
- Use a prepared statement. No ORM, extra abstractions or retry logic.

## Real MySQL tests

Three independent PDO sessions exercise:

1. **Shared + shared:** A and B hold shared locks on product 100 concurrently.
2. **Shared + UPDATE:** C cannot change that row while A/B hold shared locks
   (1-second InnoDB lock wait timeout, error 1205).
3. **Plain SELECT:** C can still perform an ordinary consistent read.
4. **FOR UPDATE + shared:** B cannot acquire a shared lock while A holds
   an exclusive lock (same short timeout).
5. Releasing locks allows an UPDATE to proceed.

The test owns all transaction boundaries deliberately so it can observe
what happens **while** a lock is still held.

The exercise contrasts shared/exclusive compatibility and consistent reads;
it does not ask you to build a job queue or a transaction orchestration engine.
