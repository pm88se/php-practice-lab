# SQL-003 — Transaction Isolation and Consistent Reads

**EAV: 20–30 minutes** · Base · MySQL 8.4 / InnoDB · PDO

## Business scenario

A report endpoint reads an account balance, performs some application work,
and then reads that balance again within the same database transaction.
Meanwhile, another request commits an update. Should the report see the new
balance on its second read?

## Implement

`Sql003IsolationObserver::observe(PDO $reader, int $accountId, string $isolation, callable $betweenReads): array`
in `mysql/src/Sql003IsolationObserver.php`.

- Only accept `READ COMMITTED` and `REPEATABLE READ`. Throw
  `InvalidArgumentException` for other strings.
- Set the isolation level of the **next transaction** on the supplied PDO
  connection, then begin that transaction.
- Run a **normal non-locking SELECT** for `accounts.balance_cents`.
- Call `$betweenReads()` **exactly once**, while the reader transaction is
  still open. The test callback commits an UPDATE from another PDO connection.
- Read the same balance using another ordinary SELECT **within the same
  reader transaction**.
- Commit and return the two integer balances as `[first, second]`.
- On error roll back your transaction and propagate the exception.
- Do not open your own connection, use `FOR UPDATE`, or combine both readings
  into a single SQL statement. Keep the implementation small.

Initial balance: **10000 cents**. The callback changes it to **9000 cents**.

## What the tests demonstrate

| Isolation level | First SELECT | Second SELECT |
| --- | ---: | ---: |
| `READ COMMITTED` | 10000 | 9000 |
| `REPEATABLE READ` | 10000 | 10000 |

For InnoDB, ordinary consistent reads at `REPEATABLE READ` use the same
transaction snapshot after the first consistent read. At `READ COMMITTED`
each ordinary SELECT may see newly committed data.

This task isolates **non-locking consistent reads**, not locking reads,
phantoms, write skew or deadlocks. Those deserve separate exercises.
