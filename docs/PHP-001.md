# PHP-001 — CSV order summary under a memory limit

- **Engineering problem:** ENG-01 — Process more data than you can comfortably keep in memory.
- **Level:** Base → Deep
- **EAV:** 20–25 minutes
- **Branch:** `drill/PHP-001`
- **Scope:** Native PHP 8.3+, CLI; no framework and no external dependency.

## Production scenario

An operations team exports order activity into CSV files. A CLI job must calculate the count and total value of **paid** orders. Small exports are easy; the same job must remain reliable when an export contains hundreds of thousands of rows and the worker has a tight memory limit.

## Contract

Implement `Practice\\CsvOrderSummary::summarize(string $path): array` in `src/CsvOrderSummary.php`.

Input CSV columns:

```csv
order_id,status,amount_cents
o-1,paid,1299
o-2,pending,500
```

Return:

```php
['paid_count' => 1, 'paid_total_cents' => 1299]
```

Count **only** rows where `status === 'paid'`. Amounts are non-negative integer cents. The CSV is valid UTF-8 with a header and no embedded newline fields. You may assume the schema and data are valid for this first drill; validation is out of scope.

## Acceptance criteria

1. Small fixture: paid count **3**, paid total **2000** cents.
2. Header-only CSV returns zeroes.
3. Generated CSV with **150,000** rows returns paid count **75,000**, total **14,925,000** cents.
4. The same tests complete with **16 MB PHP memory limit**.
5. Avoid loading the entire CSV into an array. No database, framework, queue, or third-party package.

## Run

```bash
php tests/run.php
php -d memory_limit=16M tests/run.php
```

The starter intentionally throws `LogicException`; tests are expected to be red until you implement it. The large input is generated on disk in `tests/php001.php` and deleted afterward.

## Design freedom

Pick the simplest adequate technique. Native file handles + `fgetcsv`, `SplFileObject`, or a generator-based reader are possible options; **using a generator is not mandatory**. Consider when separating traversal from aggregation would justify an iterator/generator.

## Review questions

- What is the approximate **space complexity** as input row count grows?
- What resources must be released if parsing or aggregation throws?
- In which situations would a plain `array` solution be preferable?
- What would change if rows were consumed by more than one downstream operation?

When ready, push your implementation and open a PR from `drill/PHP-001` into `main`.
