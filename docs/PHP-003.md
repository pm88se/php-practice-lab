# PHP-003 — Stable Priority-Based Job Scheduler

- **Engineering problem:** Scheduling competing tasks under priority constraints
- **Focus:** SPL data structures, priority ordering, FIFO stability
- **Level:** Base → Deep
- **EAV:** 20–30 minutes
- **Setup branch:** `setup/PHP-003`
- **Implementation branch:** `drill/PHP-003` (create from updated `main` after setup merge)

## Production scenario

A small CLI worker receives jobs for refunds, inventory sync and analytics exports. When backlog grows, urgent jobs should be processed first. But **jobs of the same priority must preserve arrival order** to avoid surprising reordering.

Build a scheduler that supports enqueueing a job and consuming the next one. This exercise is about **in-process scheduling**, not a persistent or distributed queue.

## Public API

Implement `Practice\\JobScheduler` in `src/JobScheduler.php`:

```php
$scheduler = new JobScheduler();
$scheduler->add('job-1', 'analytics_export', 1);
$scheduler->add('job-2', 'payment_refund', 10);
$scheduler->add('job-3', 'inventory_sync', 5);
$scheduler->add('job-4', 'payment_refund', 10);

$job = $scheduler->next();
```

- `add(string $id, string $type, int $priority): void` — add a job. Larger priority means earlier processing.
- `next(): ?array` — remove and return one job as `['id' => string, 'type' => string, 'priority' => int]`; returns `null` if empty.
- For equal priorities, **FIFO**: the job that arrived first must be returned first.
- Allow positive, zero and negative integer priorities.
- Job IDs are unique for this drill. No cancellation, retries, persistence or concurrency required.

## Acceptance criteria

1. Return jobs in **descending priority** order.
2. Preserve insertion order for **equal priorities**.
3. Return `null` for an empty queue, including repeated calls.
4. Support additions after some jobs have already been removed.
5. Keep the existing PHP-001/002 tests passing under the 16 MB PHP memory limit.
6. No third-party dependencies.

## Design freedom

Possible approaches: array + sort, or `SplPriorityQueue` with a tie-breaking strategy. Consider costs as the queue grows; **do not assume SPL automatically preserves FIFO when priorities tie**.

The goal is to justify your choice. Aim for efficient `add()` and `next()` without sorting the entire backlog after every extraction.
